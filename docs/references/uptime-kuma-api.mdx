## what this is

How URSA talks to an Uptime Kuma server. Kuma has no stable public API - it's a
Socket.IO app plus a few unauthenticated REST endpoints for public status pages.
Everything below was rechecked through tag `2.5.5` (`c98982a`) and captured from
digest-pinned official images for 2.4.0 and every 2.5.0-2.5.5 release. The
reproducible probe is `scripts/verify-kuma-compatibility.ps1`.
Sanitized raw captures and the complete source-derived event/route inventory live
under gitignored `docs/kuma-notes/`. Build a thin adapter around this; expect drift
between versions.

## technical map

**transport**
- Socket.IO v4 at server root (`/`). Open with **polling then upgrade**;
  websocket-first can `connect_error` on some setups.

**auth flow (all callbacks return `{ ok, msg?, msgi18n? }` + extras)**
1. Server emits `loginRequired` on connect (and `setup` if no admin exists).
2. `emit("login", { username, password, token })` → cb `{ ok, token }` (JWT).
   `token` = 2FA code; if cb returns `{ tokenRequired: true }`, re-emit with it.
3. Later sessions: `emit("loginByToken", <jwt>)` instead of credentials.

The session JWT may be imported directly and validated with `loginByToken` before
it is saved. Kuma's `uk...` API keys are not an alternative socket credential:
2.5.3 verifies them only in the HTTP Basic authorizer used by the Prometheus
endpoint. Passing one to `loginByToken` is rejected by design.

**server → client events (⚠ several are POSITIONAL args, not objects)**
- `info` is emitted without version/runtime fields before authentication, then as
  `{ version, latestVersion, serverTimezone, dbType, isContainer, ... }` after login.
- `monitorList` → `{ [id]: MonitorObject }` (id-keyed object, not array)
- `heartbeat` → `{ monitorID, status, time, msg, ping, important, retries }` (camelCase)
- `heartbeatList` → **positional** `(monitorID:String, HeartbeatRow[], overwrite:Boolean)`
- `avgPing` → **positional** `(monitorID:String, avgPingMs:Number)`; average may be fractional
- `uptime` → **positional** `(monitorID:String, periodHours:Number, fraction:0..1)`
- `certInfo` → **positional** `(monitorID:String, tlsInfoJSON:String)`; parse the second argument again
- also pushed on login: `monitorTypeList, maintenanceList, notificationList,
  proxyList, dockerHostList, apiKeyList, remoteBrowserList, statusPageList,
  initServerTimezone`

**client → server events (with ack callback)**
- `getMonitorBeats(id, periodHours)` → `{ ok, data: HeartbeatRow[] }`
  rows are **snake_case**: `{ id, monitor_id, status, msg, time, ping, duration,
  down_count, end_time, retries }`
- `getMonitorChartData(id, periodHours)` → `{ ok, data: [{ up, down, avgPing,
  minPing, maxPing, timestamp }] }` (⚠ NOT `ping/pingMin/pingMax`)
- `monitorImportantHeartbeatListPaged(null, offset, count)` →
  `{ ok, data: HeartbeatBean[] }`, newest first; these rows use camelCase
  `monitorID` and boolean `important` like the live event, not `getMonitorBeats`
  row casing. `null` selects all monitors, and 2.5.3 retains important state
  transitions separately from the rolling live list.
- `pauseMonitor(id)` / `resumeMonitor(id)` → `{ ok, msg, msgi18n }`
- `getMonitor(id)` → full MonitorObject
- `addNotification(config, notificationID|null)` returns `{ ok, id }`. Webhook
  config includes `name`, `type=webhook`, `isDefault`, `webhookURL`, and
  `httpMethod=post`. `webhookContentType=json` sends Kuma's standard body;
  `webhookContentType=custom` renders `webhookCustomBody` through Liquid. In
  2.5.3 the template context exposes `heartbeatJSON`, `monitorJSON`, and `msg`,
  and Liquid's `| json` filter produces JSON-safe values. Unknown config keys are
  retained.
- `deleteNotification(notificationID)` returns `{ ok, msg }`; Kuma removes the
  associated monitor-notification relations.
- `testNotification(fullNotificationConfig)` returns `{ ok, msg }` after the
  provider completes its send. A standard Webhook posts
  `{ heartbeat: null, monitor: null, msg: "<notification name> Testing" }`;
  a custom Webhook renders the same null monitor/heartbeat values through its
  template. Kuma does not save the temporary config.
- `editMonitor(fullMonitorObject)` returns `{ ok, msg }`. Notification assignment
  is the full object's `{ "notificationIDList": { "<id>": true } }` map. Kuma
  restarts the edited monitor, so bulk callers should update sequentially. URSA
  fetches that object immediately before save, requires its type to match the
  typed draft, and compares every non-editable field before emitting the mutation.
- `add(fullMonitorObject)` returns `{ ok, msg, monitorID }`. Push monitors require
  a 32-character alphanumeric `pushToken`; Kuma 2.4.0 through 2.5.5 generate it
  from the same 62-character alphabet. Their public heartbeat endpoint is
  `<baseURL>/api/push/<pushToken>?status=up&msg=OK&ping=`. `status` accepts `up`
  or `down`, `msg` is optional display text, and `ping` is an optional non-negative
  millisecond value. The token is a write capability and must be treated as secret.
- `getTags()` returns `{ ok, tags: [{ id, name, color }] }`.
  `addMonitorTag(tagID, monitorID, value)` and
  `deleteMonitorTag(tagID, monitorID, value)` update assignments and push an
  `updateMonitorIntoList` event. The exact value is part of the delete key.
- Group/folder membership is the full monitor object's nullable `parent` field.
  Kuma rejects assigning a group below one of its descendants. `weight` is
  emitted for sibling ordering (descending after active state), but 2.5.3 has no
  authenticated event that mutates monitor weight; clients must not invent a
  local-only order.
- `maintenanceList` is an ID-keyed object of maintenance JSON. Detail editing uses
  `getMaintenance(id)` and `getMonitorMaintenance(id)`. Create/edit returns a
  `maintenanceID`, after which `addMonitorMaintenance(id, [{ id }])` replaces the
  affected-monitor relation. `pauseMaintenance`, `resumeMaintenance`, and
  `deleteMaintenance` are separate acknowledged events.
- Maintenance strategies are `manual`, `single`, `cron`, `recurring-interval`,
  `recurring-weekday`, and `recurring-day-of-month`. Payloads use `dateRange`,
  `{ hours, minutes }` `timeRange` entries, `timezoneOption`, `intervalDay`,
  `weekdays`, `daysOfMonth`, `cron`, and `durationMinutes`.
- Authenticated public-incident operations are status-page-slug scoped:
  `postIncident(slug, { title, content, style })` creates an active pinned incident
  and returns `{ ok, incident }`; `editIncident(slug, id, { title, content, style,
  pin })` returns the updated incident; `unpinIncident(slug)` clears the page's pin;
  `resolveIncident(slug, id)` returns the now inactive/unpinned incident; and
  `deleteIncident(slug, id)` returns `{ ok }`. Supported styles are `info`,
  `warning`, `danger`, `primary`, `light`, and `dark`.
- `getIncidentHistory(slug, null)` returns `{ ok, incidents, total, hasMore }` over
  the authenticated socket. Use it after a mutation: Kuma's unauthenticated REST
  incident-history response can retain a stale cache even after the socket
  acknowledgement succeeds.

**status codes**: `0=DOWN, 1=UP, 2=PENDING, 3=MAINTENANCE`.
**time**: string `"YYYY-MM-DD HH:mm:ss.SSS"` in server tz, not epoch.

## verified compatibility matrix

URSA's stable write-verified range is 2.4.0 through 2.5.5. The probe boots each
exact digest, creates an administrator, authenticates over the real Socket.IO
polling contract, checks `info.version` and `monitorTypeList`, and removes its
container and volume. Every image exercises the complete public-incident mutation
lifecycle. At the 2.4.0 floor it also exercises monitor
create/get/round-trip edit/pause/resume/delete, maintenance
create/assign/pause/resume/delete, and Webhook notification create/delete.

Kuma 2.5.1 and 2.5.2 publish the previous release number over the socket. Their
feature boundaries are unchanged by that ambiguity: both advertise NTP/PM2 and
neither advertises SFTP. `KumaCapabilities` therefore evaluates the reported
stable version, not an invented tag. Missing, malformed, prerelease, older, and
newer versions retain safe reads but are not advertised as write-verified. Known
type-specific schemas are separately gated, so SFTP create/edit is available only
when the server reports 2.5.4 or 2.5.5.
All monitor writes also require the reported version to remain inside the global
write-verified range; a type without a special schema threshold cannot bypass that
outer gate.

Keyword monitors use the ordinary `url` endpoint plus required string `keyword`
and boolean `invertKeyword` fields. In 2.5.5, `invertKeyword = false` means the
check succeeds when the response contains the keyword; `true` reverses that test
and alerts when the response contains it. URSA exposes only these type-specific
fields for now and preserves other HTTP settings from the freshly loaded object.

JSON-query monitors use required string fields `jsonPath`, `jsonPathOperator`, and
`expectedValue`. Kuma 2.5.5 accepts operators `>`, `>=`, `<`, `<=`, `!=`, `==`,
and `contains`; the UI defaults new expressions to `$` and comparisons to `==`.
Numeric comparison values are still transported as strings by Kuma's editor.

MQTT monitors use required `hostname`, `port`, and `mqttTopic` fields, optional
`mqttUsername`, `mqttPassword`, and `mqttWebsocketPath`, and `mqttCheckType` of
`keyword` or `json-query`. Kuma prepends `mqtt://` when the host has no recognized
`mqtt`, `mqtts`, `ws`, or `wss` scheme. It supplies no default port. Keyword mode
tests `mqttSuccessMessage` as a substring and an empty string accepts any received
message. JSON-query mode evaluates `jsonPath` and compares its string result exactly
with `expectedValue`. The WebSocket path is empty or matches
`^/[A-Za-z0-9-_&amp;()*+]*$`. A non-empty `conditions` array takes precedence server-side,
so clients that do not edit conditions must preserve it unchanged.

SMTP monitors use required `hostname` and `port` fields plus nullable
`smtpSecurity`. Kuma 2.5.5 maps `secure` to SMTP over TLS, `nostarttls` to
plaintext with STARTTLS disabled, and `starttls` to a required STARTTLS upgrade
with certificate verification. The server falls back to port 25 when the wire
value is absent, but its editor requires an explicit port and URSA does not invent
that default. The monitor calls Nodemailer's transport verification only; it does
not send email or require mailbox credentials. Existing null or unknown security
values must remain opaque because converting them would silently change transport
behavior.

NTP monitors, available from Kuma 2.5.0, use required `hostname` and `port` plus
`ntpStratumThreshold`, `ntpTimeOffsetThreshold`, and
`ntpRootDispersionThreshold`. The editor defaults new monitors to UDP port 123, a
300-second interval, a 48-second timeout, and thresholds 5, 1000 ms, and 500 ms.
Stratum accepts 1 through 15; the two millisecond thresholds accept positive
integers. The checker always rejects unsynchronized stratum 16, then rejects
stratum at or above its threshold, absolute clock offset at or above its threshold,
and root dispersion at or above its threshold. Falsy server values fall back to
5/1000/500; clients must preserve explicit null values during unrelated edits
rather than silently materializing those defaults.

Globalping monitors use a subtype-specific contract. Ping sends `subtype: "ping"`,
`hostname`, one `location` magic string, nullable `ipFamily` (`ipv4` or `ipv6` when
explicit), `protocol` (`ICMP` or `TCP`), `ping_count`, and a `port` used only by TCP.
Kuma's editor initializes Ping to `world`, automatic IP family, ICMP, retained port
80, three packets, and a 48-second timeout. It accepts one location expression; `+`
may combine provider and geography filters, while comma-separated locations are not
supported. Packet count is 1 through 100 and TCP ports are 1 through 65535. URSA's
native codec owns this exact shape.

DNS sends `subtype: "dns"`, `hostname`, `location`, nullable `ipFamily`, optional
`dns_resolve_server`, required port, `dns_resolve_type`, optional `keyword`, and
`protocol` (`UDP` or `TCP`). Kuma 2.5.5 offers A, AAAA, ANY, CNAME, DNSKEY, DS,
HTTPS, MX, NS, NSEC, PTR, RRSIG, SOA, SRV, SVCB, and TXT. New drafts use
world/automatic, port 53, A, and UDP. The server treats `keyword` as a
case-insensitive JavaScript regular expression over returned records, so URSA does
not apply an incompatible JVM-regex validator.

HTTP sends `subtype: "http"`, `url`, `location`, nullable `ipFamily`, optional
resolver, nullable protocol (automatic) or `HTTP2`, `method` (`HEAD`, `GET`, or
`OPTIONS`), JSON-encoded accepted status codes, `ignoreTls`, `expiryNotification`,
`cacheBust`, response-check fields, JSON-encoded request headers, and optional
Basic, Bearer, or OAuth2 client-credentials authentication. Kuma does not offer mTLS
for this subtype. URSA reuses its eight-entry validated header model and
presence-only secret state: saved values never enter editable fields, blank
unchanged entries are recovered only from the fresh full object, and changing or
removing an entry or method clears superseded secrets. Keyword and JSON-query
response checks are mutually exclusive on save. Unknown subtypes, future enum
values, unsupported authentication, and future header shapes remain opaque.

Database monitors share `databaseConnectionString`. PostgreSQL, MySQL/MariaDB,
Microsoft SQL Server, and MongoDB also use `databaseQuery`; a blank SQL query falls
back to `SELECT 1`, while a blank MongoDB query runs `{ "ping": 1 }`. MongoDB passes
a parsed JSON object to the driver command and can evaluate `jsonPath` with JSONata
before comparing its string result with `expectedValue`. MySQL can supply a separate
`radiusPassword` override. Redis uses `ignoreTls` and has no query field. MySQL and
SQL Server can also carry recursive result `conditions`; clients without the exact
condition editor must preserve that array unchanged. Connection strings and the
MySQL override can contain credentials and therefore must not be prefilled, logged,
or copied into local monitor caches.

WebSocket-upgrade monitors use a `ws`/`wss` `url`, optional comma-separated
`wsSubprotocol`, boolean `wsIgnoreSecWebsocketAcceptHeader`, and string-array
`accepted_statuscodes`. Kuma 2.5.5 offers every individual close code from
`1000` through `4999` and defaults new monitors to `["1000"]`; its server splits
subprotocols on commas and removes whitespace. The full object may also contain
`headers` as a JSON-encoded object. URSA's structured editor supports up to eight
unique HTTP-token names with string values; it masks saved values and reconstructs
unchanged entries from the fresh full object. Malformed JSON, non-string values,
case-insensitive duplicates, and larger objects remain opaque. Authentication
uses nullable `authMethod`: `basic` pairs `basic_auth_user` with
`basic_auth_pass`, while `bearer` uses `bearer_token`. URSA reduces returned
passwords/tokens to presence flags before UI state, retains a blank saved value
only while the method is unchanged, and clears the superseded fields when the
method changes. OAuth client credentials (`oauth2-cc`) use
`oauth_auth_method` (`client_secret_basic` or `client_secret_post`),
`oauth_token_url`, `oauth_client_id`, `oauth_client_secret`, `oauth_scopes`, and
`oauth_audience`. mTLS (`mtls`) uses `tlsCert`, `tlsKey`, and optional `tlsCa`.
URSA keeps OAuth client secrets and all returned PEM material out of editable
state, retains blank saved values from the fresh full object, and offers an
explicit removal control for the optional CA. Deliberately changing auth methods
clears the superseded fields; ordinary edits preserve dormant legacy fields.

Kuma exposes no idempotency key for `postIncident`. A lost create acknowledgement
is therefore an unknown outcome: refresh incident history before allowing another
create instead of automatically replaying it.

Kuma 2.5.0 adds `ntp` and `pm2` monitor types plus the authenticated
`getPM2ProcessList` event. Those additions do not change URSA's read,
heartbeat-history, certificate, pause, or resume contracts.

Kuma 2.5.1 adds seven outbound notification providers: SMS Gateway, ClickUp,
TurboSMTP, BearSMS, Pinglet, Milky, and OpenWA. They do not change the Webhook
provider payload URSA consumes. Kuma 2.5.2 fixes non-Docker installation, and
2.5.3 corrects the published version number. Kuma 2.5.4 adds the `sftp` monitor
type, Signalgrid, Notify!, and Amoot SMS providers, plus a cached-response fix.
SFTP monitor objects add `sftpPath`, `sshAuthMethod`, `sshUsername`, `sshPassword`,
`sshPrivateKey`, and `sshPassphrase`; common edits must retain these fields from
the fresh full object. Kuma 2.5.5 fixes a TCP monitor socket leak without changing
the client contract. Across 2.5.0 through 2.5.5, the source inventory remains 87
client events, 30 server emit candidates, and 33 REST routes. Previously consumed
live payload shapes are unchanged; the full monitor shape and `monitorTypeList`
gain only the SFTP additions.

**REST (no auth - public status pages)**
- `GET /api/status-page/<slug>` - page config, public groups/monitors, pinned
  active incidents, and active maintenance entries
- `GET /api/status-page/heartbeat/<slug>` - up to 100 public heartbeat rows per
  monitor plus `{"<monitorId>_24": <fraction>}` uptime values
- `GET /api/status-page/<slug>/incident-history` - paginated active and resolved
  incidents as `{ ok, incidents, total, nextCursor, hasMore }`
- `GET /api/entry-page` - `statusPageMatchedDomain` returns `statusPageSlug`;
  `entryPage` can return `statusPage-<slug>` for a configured default page

## gotchas

- **Case split**: live `heartbeat` event is camelCase; `getMonitorBeats` rows are
  snake_case. The data model must map both to one domain type.
- **String IDs in positional events**: monitor IDs are JSON strings in live 2.5.3
  through 2.5.5 `heartbeatList`, `avgPing`, `uptime`, and `certInfo` emissions even
  though IDs inside object payloads are numbers. Normalize both forms at the
  adapter boundary.
- **Double-encoded JSON**: notification `config` and monitor `tags` arrive as a
  JSON string *inside* the JSON - parse twice.
- **Sensitive full monitor shape**: authenticated `getMonitor` includes fields
  needed to edit every monitor type and may include credentials. Keep it ephemeral,
  never log/store it, preserve unknown fields, and mutate only the intended field.
- **Public incident overlap**: a pinned active incident is returned by both the
  main page endpoint and incident history. De-duplicate by numeric incident ID.
- **Public incident cache**: the REST history endpoint can lag an acknowledged
  authenticated write. A mapped authenticated viewer should refresh through
  `getIncidentHistory`; an unmatched public page has only the cached REST view.
- Monitor `add` (M2+) requires a NOT-NULL `conditions` field (stringified JSON
  array) on Kuma 2.x - absent from the wiki.
- Kuma 2.x boots into a separate "setup-database" mode; the app socket isn't
  mounted until a DB is chosen. Only relevant for spinning up dev instances
  (seed `data/db-config.json = {"type":"sqlite"}`), never for the app itself.
- Self-signed certs are common in this userbase - handle TLS trust explicitly.
