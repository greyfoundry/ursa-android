## what this is

The running change log across sessions - project memory over time. Append a dated
entry every session that changes structure. Newest at top.

### 2026-08-25 - encrypted access headers

**changed**: Completed parity item CP-004. Connection forms now include a
collapsed access-header editor with masked Cloudflare Access Client ID/Secret
fields and up to eight custom name/value pairs. Validated headers are encrypted
inside each saved connection, applied to Socket.IO polling/WebSocket handshakes,
available to status-page REST requests, and reused by notification actions.
Saved-server summaries reveal only a count.

**security boundary**: Header names must use the HTTP token character set; values
must be non-empty and cannot contain CR/LF; duplicates and partially completed
pairs disable connection actions. Passwords, TOTP values, session JWTs, and
header values are never logged or rendered in summaries.

**verification**: Added focused normalization/injection tests and exercised the
form on the emulator. A temporary Socket.IO server returned login success only
when the expected custom header arrived in its handshake; URSA's connection test
passed through that gate. The temporary container was then removed.

### 2026-08-25 - imported Kuma session authentication

**changed**: Completed parity item CP-003. Connection and re-authentication forms
now switch between password/2FA and a masked Kuma session-token mode. Imported
tokens are validated with `loginByToken` before encrypted persistence, and failed
validation leaves the active session untouched. The UI explicitly explains that
Kuma API keys cannot open its live socket.

**contract boundary**: Uptime Kuma 2.5.3 source verifies `uk...` API keys only in
the HTTP Basic authorizer used by Prometheus. Its socket accepts server-signed
JWTs through `loginByToken`; URSA implements that real contract and does not
invent an API-key exchange.

**verification**: The token form, masked semantics, mode switch, and rejected
token result were exercised on the emulator against an ephemeral official Kuma
2.5.3 instance. Existing stored JWT reconnect continues through the same
`loginByToken` client path.

`onNewEndpoint`, and on `onMessage` parses Kuma's webhook JSON and posts a system
notification (permission-guarded, channel `ursa_monitors`). `PushParse` = pure,
tolerant parser of `{heartbeat, monitor, msg}` → `PushNotice`. `PushStore` =
process-wide endpoint/distributor holder (SharedPreferences + StateFlow).

**decisions made**:
- **`PushService`, not the deprecated `MessagingReceiver`** - verified against
  connector 3.3.3 source. Bonus: it's `exported="false"`, so the M3 security gate
  (no exported push surface) is satisfied by construction.
- No VAPID/web-push encryption: Kuma POSTs plain JSON, so messages arrive
  unencrypted (`decrypted=false`); push body treated as untrusted, render-only.
- Endpoint URL kept in plain SharedPreferences (delivery address, not a credential).
