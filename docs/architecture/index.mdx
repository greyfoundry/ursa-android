## what this is

How URSA is wired together and how data flows from a Kuma server to the screen.
The app is a thin, reactive client: a socket/REST layer feeds repositories,
repositories expose Flows, and Compose renders them. URSA has no separate backend;
explicit management actions write only to the user's authenticated Kuma server.

## technical map

**data flow**
```
Kuma server ──Socket.IO──▶ core.network (adapter: parse/normalize wire → domain)
            ──REST(Ktor)─▶        │
                                  ▼
                          data.repository (StateFlow<DomainModel>, single source of truth)
                                  ▼
                          ui.* (Compose, collectAsStateWithLifecycle)

core.storage (DataStore+Tink)  ── credentials/JWT ──▶ core.network (login/loginByToken)
             └─ encrypted monitor snapshots ──▶ data.repository.FleetRepository
distributor (ntfy) ──push──▶ core.push (UnifiedPush receiver) ──▶ system notification
core.push (validated endpoint) -> data.repository -> core.network -> Kuma Webhook provider
```

**layers**
- `core.network` → `.../core/network/` (KumaClient, KumaParse, StatusPageClient) -
  see `docs/modules/network.mdx`.
- `core.storage` → `.../core/storage/` (ConnectionStore, encrypted caches,
  preferences, event history, and incident notes) - DataStore with Tink
  AES-256-GCM at rest, master key in Android Keystore.
- `core.push` → `.../core/push/` (UrsaPushService, PushParse, PushStore,
  ManagedPushScopeStore, KumaWebhook, PushDeliveryTest) - UnifiedPush receive path,
  encrypted provider/server scope binding, delivery URL validation, privacy-safe
  diagnostics/testing, and notification rendering.
  See `docs/modules/push.mdx`.
- `data.model` → `.../data/model/` - server/monitor/status-page models plus
  `FleetModels.kt` for cache availability, freshness, normalized counts, and typed
  transport/authentication/managed-push health states.
- `data.repository` → `.../data/repository/MonitorRepository.kt` owns the active
  socket; `FleetRepository.kt` reads saved connections and encrypted snapshots
  without connecting to inactive servers on load. Its explicit refresh uses at
  most two short-lived clients and closes them after per-server results are captured.
- `ui.*` → `.../ui/` (UrsaViewModel, UrsaApp, typed Navigation 3 shell,
  cache-first fleet Home with explicit bounded refresh and server-scoped drill-down,
  expandable privacy-safe server health,
  Material 3 Adaptive navigation/list-detail, shared operational components,
  connections/monitors/statuspage) -
  see `docs/modules/ui.mdx`.
- app shell → `.../MainActivity.kt` - see `docs/modules/app-shell.mdx`.
- update check -> `.../core/update/` - user-triggered official GitHub release lookup,
  strict semantic version parsing, and optional version-deduplicated notification.
- Wear companion -> standalone public polling plus an optional same-signed Data Layer
  session handoff - see `docs/modules/wear.mdx`.

**depends on**
- `docs/references/*` - the external API contracts each layer implements against.

## gotchas

- The adapter in `core.network` is the ONLY place that knows Kuma's wire quirks
  (positional events, snake/camel split, double-encoded JSON). Keep it there.
- One `Socket` per active server; multi-server = switch the active repository, not
  multiple permanent live sockets. Cached Fleet loading performs no network work;
  explicit Fleet refresh uses only bounded, short-lived sessions.
- Push is independent of the socket - it works while the app is closed, via the
  distributor. Don't couple them.
