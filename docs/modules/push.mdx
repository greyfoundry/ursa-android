## what this is

Push notifications via **UnifiedPush** - a monitor goes down, Kuma POSTs to a push
endpoint, the distributor (e.g. ntfy) delivers it to the app, and URSA renders a
system notification. No relay server, no Firebase. Independent of the Socket.IO
connection: push works while the app is closed.

## technical map

**file paths**
- `.../core/push/UrsaPushService.kt` - extends the connector's `PushService`
  (a Service, NOT exported). Captures the endpoint (`onNewEndpoint`), renders a
  notification from the webhook body (`onMessage`), handles failure/unregister.
- `.../core/push/PushParse.kt` - pure, tolerant parser of Kuma's webhook JSON
  (`{heartbeat, monitor, msg}`) → `PushNotice`. JVM-unit-tested (`PushParseTest`).
- `.../core/push/PushStore.kt` - process-wide holder of the endpoint URL + chosen
  distributor plus privacy-safe diagnostic/test metadata (SharedPreferences
  mirrored into StateFlows).
- `.../core/push/KumaWebhook.kt` - validates the registered delivery endpoint and
  adds ntfy's required `up=1` query flag without discarding an existing query.
- `.../core/push/PushDeliveryTest.kt` - creates and exactly matches the short,
  random marker used to distinguish a requested Kuma test from unrelated pushes.
- `.../core/push/PushPathHealth.kt` - pure resolver for distributor registration,
  managed Kuma setup, connection failure, and bounded delivery-test health. It
  also distinguishes explicit disconnects from unexpected unregister callbacks.
- `.../core/push/PushAlertModeStore.kt` - synchronous, server-scoped local policy
  for transition modes, severity, bounded timing, and snooze expiry.
- `.../core/push/PushEffectivePolicy.kt` - pure resolver for effective values,
  source precedence, current delivery blockers, dependency suppression, quiet
  hours, and snooze timing.
- `.../core/push/PushDependencyStore.kt` - encrypted, versioned per-server
  dependency graph with bounded multi-parent rules and cycle-safe evaluation.
- `.../core/push/ManagedPushScopeStore.kt` - encrypted, versioned binding from a
  managed provider's random server scope to the exact saved connection and a
  bounded lightweight monitor directory, plus the pure unknown-provider/monitor
  classifier used at the delivery boundary.
- `.../core/push/PushAlertLifecycle.kt` - pure delay/repeat/acknowledgement policy
  plus privacy-safe WorkManager and notification identities.
- `.../core/push/PushPendingAlertStore.kt` - encrypted rendered payloads for
  delayed and repeating alerts; active pointers contain only random server scope,
  monitor ID, and opaque alert ID.
- `.../core/push/PushAlertWorker.kt` - one-shot scheduled delivery and bounded
  repeat chaining. WorkManager input contains only an opaque alert ID.
- `.../core/push/PushAlertActionReceiver.kt` - non-exported acknowledge and
  one-hour snooze notification actions.
- `.../core/push/PushNotificationGrouping.kt` - same-server Android grouping,
  bounded inbox summaries, detached-child reconciliation, and optional
  evidence-bounded storm hints; dismissal reconciliation remains non-exported.
- `.../core/push/PushQuietHours.kt` / `PushQuietHoursStore.kt` - local weekly
  schedule that routes delivery-time alerts to the existing silent channel.
- `.../core/push/PushEventPolicy.kt` / `PushEventPreferencesStore.kt` - recovery,
  maintenance, certificate, and update opt-ins plus stable event-channel routes.
- `.../core/push/PushTransitionStore.kt` - server-scoped two-minute exact-transition
  de-duplication and latest received monitor statuses; real status changes always
  pass.
- `.../core/push/OverallStatusService.kt` - optional special-use foreground service
  that keeps a direct authenticated socket and an ongoing live fleet notification.
- `.../ui/push/PushScreen.kt` - pick a distributor, request `POST_NOTIFICATIONS`,
  show/copy the endpoint, create or update the marked Kuma Webhook provider,
  select existing monitors/default use, configure per-monitor alert modes and
  delivery severity, timing, and dependencies, explain the resulting policy, show
  setup status and safe failure hints, and remove it safely. Per-monitor actions wrap into compact rows
  instead of creating a tall trailing button column. The setup
  summary names the exact saved connection, managed Webhook provider, UnifiedPush
  distributor, and last end-to-end test outcome in one place. Duplicate marked
  Webhooks expose one Remove-then-Create repair path instead of guessing which
  provider owns assignments.

**exports**
- `UrsaPushService` (manifest-declared, `exported="false"`, action `PUSH_EVENT`).
- `PushParse.parse(raw): PushNotice?`.
- `PushStore.endpoint` / `.distributor` (StateFlow), `load`/`setDistributor`/
  `clear`; `diagnostics` exposes timestamps and normalized result
  categories without retaining endpoint copies or message contents.
- `ManagedPushScopeStore.bind/load/remove` persists only server URL plus bounded
  monitor ID/name/type/parent/tag/active metadata after managed setup is verified.
- `KumaWebhook.deliveryUrl(endpoint, distributor)` returns a validated HTTP(S)
  endpoint ready for Kuma, or null.
- ViewModel: `pushEndpoint`, `pushDistributor`, `distributors`, `pushMode`;
  `enterPush`/`exitPush`/`refreshDistributors`/`registerPush`/`unregisterPush`,
  plus local notification testing, managed Kuma setup state, and
  create/update/test/remove actions, per-monitor alert-mode state, and the
  server-scoped storm-correlation opt-in.

**depends on**
- `org.unifiedpush.android:connector:3.3.5` (excludes JVM `tink`; we ship
  `tink-android`). See `docs/references/unifiedpush.mdx` (verified from source).
- `androidx.core` (NotificationManagerCompat), `MainActivity` (content intent).

## gotchas

- **`PushService`, not `MessagingReceiver`** (the latter is deprecated). The service
  is `exported="false"` - the connector's own internal receiver forwards to it - so
  there is no exported push surface to harden.
- No VAPID / web-push encryption: Kuma sends plain JSON, so `PushMessage.decrypted`
  is false and `content` is the raw body. The body is untrusted input and parsed
  tolerantly. Manual and legacy payloads are render-only. A payload carrying a
  locally bound managed scope may update non-sensitive local transition state used
  for de-duplication, recovery cleanup, and opt-in dependency suppression; it can
  never authorize a remote mutation.
- `POST_NOTIFICATIONS` is a runtime permission on API 33+; the service drops the
  notification (logs a warning) if it isn't granted. `PushScreen` requests it.
- ntfy endpoints need `up=1` so ntfy forwards Kuma's raw bytes. Managed setup adds
  it automatically and preserves any existing endpoint query parameters.
- URSA only edits or removes Webhook providers whose double-encoded config contains
  the exact `ursaManaged: true` marker. The provider is named `URSA UnifiedPush`;
  unrelated user notification providers are not surfaced to the managed setup path.
- Managed providers use Kuma's custom Webhook body with Liquid's JSON filter and a
  random 32-hex `ursaServerId`. The scope is not a credential and is never shown;
  it prevents identical monitor IDs on different saved servers from sharing an
  alert policy. A current provider is also bound locally to its exact saved
  connection in encrypted storage. Legacy managed providers are bound when the
  authenticated setup screen verifies them. A managed identity is trusted only when
  both provider and monitor exist in that binding. Unknown-provider/monitor payloads
  retain immediate notification delivery but are stripped of server identity before
  policy, timing, grouping, history association, and action construction. One fixed,
  privacy-safe warning opens Notifications; a verified refresh clears it.
- Per-monitor modes are non-sensitive device preferences keyed by server scope and
  monitor ID. Muted posts nothing; down-only accepts status 0; down-and-recovery
  accepts 0 and 1; all-transitions also accepts pending, maintenance, and unknown
  legacy payloads. Manual or legacy Webhooks without a valid scope default to all
  transitions so an upgrade cannot silently suppress alerts.
- Each managed monitor can explain its effective Down, recovery, and maintenance
  behavior from the same mode, severity, timing, quiet-hours, snooze, assignment,
  dependency, setup, and Android-notification state used by delivery. The resolver
  has stable `monitor > tag > group > server > default` precedence for later policy
  scopes; today only default and monitor values are persisted, so the UI says the
  other scopes are unconfigured instead of implying rules that do not exist.
- Dependency suppression is explicit opt-in and limited to monitors currently
  assigned to the same verified managed provider. A monitor may have up to 32
  parents. Edits and reads reject cycles; corrupt graphs fail open. A bound Down
  event is suppressed only while a configured parent was last received as Down.
  The exact parent is shown in policy explanation, and the suppressed event is
  appended to encrypted local history. Delayed and repeated alerts re-check the
  graph at delivery time. Unknown and legacy payloads never use dependency rules,
  preserving the released immediate-delivery behavior.
- Locally bound managed alerts share a stable group derived from a hash of the
  random server scope. The first alert posts immediately without a summary. A
  second active alert adds one Android inbox summary with at most five sanitized,
  96-character title lines; manual, legacy, delivery-test, and unbound payloads
  stay ungrouped. Acknowledge, recovery, snooze, and dismissal refresh the summary.
  When only one alert remains, it is detached before the summary is cancelled so
  Android cannot remove the surviving child with its former group. A private
  non-sensitive group marker lets a later second alert reattach that child before
  recreating the summary; serialized reconciliation prevents concurrent deliveries
  from losing group membership.
- Storm correlation is a separate, off-by-default, per-server presentation option.
  It considers only active managed Down notifications received within two minutes.
  The summary says alerts *may* share a failure domain when at least three share a
  Kuma parent, at least three share a tag, or at least five belong to the same
  server. It uses the existing encrypted managed monitor directory plus notification
  IDs, numeric statuses, and timestamps; it adds no payload persistence and never
  suppresses a child. Manual, legacy, delivery-test, unbound, Up, and stale alerts
  cannot contribute.
- Per-monitor severity uses the same server scope. Critical, standard, and silent
  map to stable Android channels. Critical defaults to high importance with sound
  and vibration; standard defaults to normal importance with sound and no forced
  vibration; silent defaults to low importance without sound or vibration. Android
  system settings remain authoritative after channel creation. Existing records
  default to critical so upgrades preserve the previous alert strength.
- Managed down alerts may be immediate or delayed by 1, 5, or 10 minutes, then
  optionally repeat every 5, 15, or 30 minutes up to 1, 3, or 5 times. Defaults
  remain immediate with no repeat. Timing preferences contain no notification
  content. Rendered pending content is encrypted with the same Keystore-backed
  AEAD as other private local state, while WorkManager receives only a random ID.
- Recovery always cancels delayed/repeating work and clears an active snooze before
  transition filtering, so a down-only policy cannot leave a stale down reminder.
  Acknowledge cancels the active alert; snooze hides it and schedules it once for
  one hour later. Both actions use immutable PendingIntents targeting a non-exported
  receiver. Manual and legacy Webhooks stay immediate because they lack the server
  scope required for collision-safe per-monitor policy.
- Quiet hours are a device-wide weekly push schedule with configurable start/end
  times and selected days. Same-day and overnight windows are supported. Alerts
  are never discarded: the effective severity becomes silent at actual delivery
  time, including delayed or repeated work. Android Do Not Disturb remains
  authoritative and the UI links to its settings without requesting policy access
  or claiming that URSA can bypass it.
- Custom sounds and vibration are delegated to Android's settings for the stable
  critical, standard, and silent channels. The Notifications screen links directly
  to each channel. URSA stores no content URI and never recreates a channel, so a
  user's custom choice survives app updates and remains under system control.
- Recovery and maintenance have separate stable channels and independent opt-ins.
  Certificate reminders can also be disabled; their existing daily worker exits
  without reading cached certificate details when disabled. The update opt-in and
  channel are ready for the CP-044 manual update checker; no network lookup is made
  by this alert-policy layer.
- Managed push transitions keep only status and timestamp under the random server
  scope and monitor ID. An exact same-status delivery inside two minutes is ignored;
  status changes always deliver, including down -> recovery -> down, and the window
  is anchored to the first delivery rather than extended by duplicates.
- Persistent status is explicit opt-in. It runs a visible `specialUse` foreground
  service with a separate low-importance channel, maintains a direct Socket.IO
  connection to the active saved server, and shows up/down/pending/maintenance
  counts with an app content intent. The UI states its battery cost. Turning it off
  stops the service and socket immediately; push delivery does not depend on it.
- Existing-monitor assignment reads are capped at four concurrent requests. Writes
  run sequentially because Kuma restarts a monitor after `editMonitor`; this avoids
  a fleet-wide restart burst. No-op relations are skipped.
- Removing managed setup deletes only marked providers. The UnifiedPush registration
  and endpoint remain on the device, ready for another server or manual setup. Removing
  a saved connection also deletes its encrypted scope and scoped local policy/work so a
  later delivery cannot retain actions for a server the user removed.
- "Test phone notification" exercises Android permission, app notification state,
  channel state, and posting only. It never contacts Kuma or the distributor.
- "Test through Kuma" sends a temporary marked Webhook config through Kuma's
  `testNotification`. A random 12-character marker correlates the returning message;
  it is cleared on match, failure, unregister, or disconnect and is never shown.
- Diagnostics persist only last registration/message/error timestamps, normalized
  registration and scope-repair categories, the last unexpected-unregister timestamp,
  test results, and the random non-credential server scope needed to clear only the
  verified repair. The scope is never rendered. Payloads, monitor names, endpoints,
  monitor IDs, and server URLs are not retained.
  Connector-confirmed registration failures and unexpected unregister callbacks use
  one normal-priority Android channel with fixed, category-only copy; explicit user
  disconnects are marked briefly and stay quiet. A successful endpoint or delivered
  message clears the warning. The setup screen reports provider/setup and known Kuma
  connection failures separately, and turns an accepted unmatched delivery test into
  a timeout after 30 seconds without adding polling or a background service. A
  delivery test does not add a fake incident to the event log.
- Kuma 2.5.1's Pinglet and SMS Gateway additions are separate outbound providers;
  the existing Webhook provider still sends the same `{ heartbeat, monitor, msg }`
  body, verified live through Kuma 2.5.5. URSA should keep the provider-neutral
  Webhook to UnifiedPush path rather than depend on a third-party provider.
- Managed alerts derive a stable, hashed notification ID from server scope and
  monitor ID, so a new status replaces the old one without colliding across servers.
  Manual legacy payloads retain the previous monitor-ID fallback.
- Down-to-recovery duration state is scoped by the same server ID when available;
  manual/legacy payloads retain the released monitor-only fallback.
- A notification that is actually posted is also appended to the encrypted,
  bounded device event log. A verified local scope binding supplies the exact saved
  server URL; unknown or legacy payloads remain provider-neutral rather than being
  guessed. Missing notification permission produces neither a notification nor a
  false history entry.
- Pause/Resume actions are created only for a locally bound managed provider and
  carry its exact saved server identity to the non-exported receiver. The receiver
  re-resolves that connection, enforces its current Access Profile and cleartext
  policy, then opens a bounded short-lived socket. It never falls back to whichever
  server happens to be active.
- Notification content and monitor actions use immutable PendingIntents with explicit
  app-owned activity/receiver components.
- Notification content routes through strict `ursa://` deep links. Private monitor
  routes contain only a one-way server scope and monitor ID; update notices open the
  validated official release page and never download or install an APK.
- Notifications use the branded monochrome `ic_stat_ursa` small icon and
  `NotificationCompat` for consistent behavior across supported Android versions.
