## what this is

The screens and the single ViewModel behind them. One `UrsaViewModel` holds all
app state; a top-level `when` in `UrsaApp` picks the screen from that state (no
navigation library for M1 - the screen set is small and state-driven).

## technical map

- `.../ui/UrsaViewModel.kt` - AndroidViewModel; owns `MonitorRepository` +
  `StatusPageClient`; login, saved-server, and saved public-page flows, selection,
  status-page state, pause/resume, and per-server favourites.
- `.../ui/UrsaApp.kt` - root; holds a minimal startup loading bridge while the
  encrypted saved-session route is restored, then routes server manager /
  status-page / login / detail / list.

  imported session-token authentication, conditional 2FA, connection test, and

## gotchas

- Routing is a `when` on state, not a nav graph. System back is handled per-screen
  with `BackHandler` (detail → list, server form → server manager, status
  page → login).
- Startup routing remains behind the one-way `startupReady` gate until encrypted
  saved connections have been read and any selected client has been activated.
  It does not wait for the network authentication acknowledgement. Routing then
  uses `hasSession` (set once authenticated, and optimistically at startup if a
  stored JWT exists) - NOT raw connection state - so reconnects keep the list
  visible with a "Connection: …" banner. `logout()` clears it.
- Saved public pages are encrypted by `StatusPageStore`; public-page URLs never
  duplicate access headers. A page whose normalized base URL exactly matches a
  saved server inherits that server's encrypted headers only at request time.
- Connection summaries show only the number of encrypted access headers. Header
  values are masked during entry and never rendered after save.
- Portable backups merge servers by normalized URL. They include connections,
  access headers, favorites, dynamic-colour choice, and slow-alert preferences;
  session JWTs require an explicit opt-in. Device-bound lock keys, push endpoints,
  cached monitor data, and alert cooldown timestamps are never exported.
- Fleet reliability statistics merge the rolling live heartbeat window with one
  bounded on-demand page of Kuma's durable important transitions. Outages that
  overlap a selected window contribute only their
  in-window duration; carry-in incidents are excluded from MTTR and flakiness.
  Coverage is conservative: any active monitor without a heartbeat at or before
  the window boundary marks the aggregate partial and warns that totals may be low.
- Incident notes are encrypted locally and keyed by server, monitor, and durable
  down-transition time. A blank save deletes the note; notes are capped at 500
  entries and 2,000 characters each and stay out of portable backups. Sharing
  uses Android's text sharesheet and omits app-held connection metadata; URL and
  credential-like values in user/server text are redacted before handoff.
- The certificate dashboard reflects live `certInfo` events for the active Kuma
  server. It distinguishes expiry from other certificate-invalid states, uses
  Kuma's 14-day reminder threshold for "expiring soon", and does not invent rows
  for HTTPS monitors whose certificate event has not arrived.
- Domain grouping parses only absolute HTTP, HTTPS, WS, or WSS URLs on supported
  HTTP-family monitor types. It strips URL user-info and all path/query/fragment
  data before display, folds default ports, preserves non-default ports and IPv6,
  and excludes malformed or hostless addresses. TLS coverage counts only secure
  monitors and remains explicit when Kuma has not emitted every certificate.
- The event log does not invent a timestamp for a current status or pause that
  predates URSA's observation. State, recovery, and maintenance entries derive
  from adjacent Kuma heartbeats. Successful pause/resume actions and notifications
  actually posted by URSA are encrypted locally, capped at 500 entries, retained
  for 90 days, and excluded from portable backups. UnifiedPush payloads do not
  identify their originating server, so those entries are provider-neutral.
- The 30-day fleet summary asks Kuma for its own 720-hour aggregate buckets only
  when opened or refreshed. Paused monitors are excluded before requests; active
  monitors with empty or failed responses remain visible in coverage counts but
  not the result. Each contributing monitor is weighted equally so a short check
  interval cannot dominate the fleet. Per-monitor rows expose the inputs, and the
  UI states Kuma's maintenance-as-up and pending-as-down semantics.
- The live panel reuses the active server's persisted favourite monitor IDs as
  its pin set. It displays only heartbeat and status data already delivered over
  the normal live connection, caps each compact strip at 16 checks, and adds no
  background polling or new persisted monitor metadata.
- Adaptive launcher and monochrome icons are packaged. Cleartext HTTP is enabled
  in the manifest for self-hosted http instances.
- UI/UX direction, accessibility requirements, and performance gates live in
  `docs/planning/ui-revamp.mdx`. The revamp is active; primary screens may be at
  different migration stages until that programme completes.
